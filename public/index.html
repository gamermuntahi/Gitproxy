How GitHub file resolution works

  1. 1

    Parse the request

    The server splits /owner.repo/ into a GitHub username and repository, plus an optional branch and file path.

  2. 2

    Validate strictly

    Username, repository, branch and every path segment are checked against strict patterns. Only GitHub identifiers are accepted — never an arbitrary URL.

  3. 3

    Fetch raw content

    The backend requests raw.githubusercontent.com///HEAD/. The HEAD ref resolves the default branch automatically — no API call.

  4. 4

    Stream it back

    The file is returned through this domain with a correct Content-Type and cache headers, so the browser loads it exactly like any other asset.

Built for static sites, safely

Real assets, same origin

Because every file is served through this domain, relative CSS, JS, image, font, SVG and JSON references in index.html resolve back to the same host.

Correct MIME types

HTML, CSS, JavaScript, JSON, SVG, PNG, JPEG, WebP, ICO and WOFF/WOFF2 are all returned with the right content type — never everything as plain text.

SSRF & traversal protection

The backend can only ever contact GitHub-owned hosts. Redirects are re-checked, path traversal is rejected, and headers are sanitised.

Vercel CDN caching

Static files are cached at the edge with Cache-Control and s-maxage, so repeat visits barely touch GitHub.

Stateless by design

No database, no accounts, no repository registration. The URL alone is enough to know which file to serve.

Friendly errors

Missing repository, private repository, bad URL format and rate limits all return clean status codes with a readable page.
