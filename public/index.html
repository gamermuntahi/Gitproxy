How It Works

Four steps from a public folder of files to a live website.

  1. 01

    Point at your source

    Choose a public GitHub repository or a public Google Drive folder. Nothing is uploaded, registered or copied.

  2. 02

    Get a real URL

    The generator composes a WebProxyLive URL that fully describes the source. The URL is the configuration.

  3. 03

    Files are fetched safely

    A Vercel Python function validates every identifier, builds the upstream request itself and enforces an allow-list. No user-supplied URL is ever fetched.

  4. 04

    Served as a website

    Correct MIME types, HTTP caching and relative paths mean CSS, JavaScript, images and fonts all load normally.

Guide

Hosting a GitHub repository

Any public repository with an index.html can be served.

  1. 1

    Make sure the repository is public

    Open the repository on GitHub and check the visibility label under its name. Private repositories return 404.

  2. 2

    Add an index.html

    Put index.html where you want the site to start - usually the repository root.

  3. 3

    Copy the repository name

    You need owner/repository, for example octocat/Hello-World.

  4. 4

    Build the URL

    Use /<owner>.<repository>/ - a dot between the two names, then a trailing slash.

  5. 5

    Pick a branch if you need one

    Add @branch before the slash: /owner.repo@gh-pages/. Without it, the default branch is detected for you.

  6. 6

    Link to deeper files

    Append the path: /owner.repo/about.html or /owner.repo/css/style.css.

  7. 7

    Share the link

    Relative paths inside the repository keep working, so the live site behaves like a normal static site.

URL shapes

/octocat.Hello-World/              root → index.html
/octocat.Hello-World/about.html    a specific file
/owner.repo@gh-pages/              a named branch
/owner.repo/css/style.css          nested assets
/owner.repo/docs/                  folder → index.html
/octocat.Hello-World/ Root page /gamermuntahi.MyWebsite/about.html Nested page /gamermuntahi.MyWebsite/css/style.css Stylesheet
Guide

Hosting a Google Drive folder

Any folder shared with Anyone with the link can be served - no API key required.

Sharing is the whole security model. Anything in a public folder is readable by anyone who has the URL. Never put private documents in a folder you host.
  1. 1

    Create or open a folder

    In Google Drive, make a folder for the site. Use plain file names with normal extensions.

  2. 2

    Add index.html

    Upload your files and place index.html directly in the folder root.

  3. 3

    Share it publicly

    Right-click the folder → Share → General access → Anyone with the link. Set it to Viewer.

  4. 4

    Copy the folder link

    It looks like https://drive.google.com/drive/folders/FOLDER_ID.

  5. 5

    Build the URL

    Use /drive/FOLDER_ID/. The generator accepts the whole link and extracts the ID for you.

  6. 6

    Use relative paths

    Link CSS and images relatively: <link href="style.css">. Nested folders resolve inside the selected folder only.

  7. 7

    Watch the size

    Individual files above 25 MB may trigger a Drive download warning page instead of streaming. Keep site assets small.

URL shapes

/drive/FOLDER_ID/                 root → index.html
/drive/FOLDER_ID/about.html       a specific file
/drive/FOLDER_ID/css/style.css    nested assets
/drive/FOLDER_ID/docs/            subfolder → index.html

Checklist

  • Folder set to Anyone with the link
  • index.html in the folder root
  • File names free of # and ?
  • Each asset under 25 MB
  • No private or sensitive files in the folder

        Architecture

        A proxy, not a host

        Requests are resolved on demand. Nothing is stored.

        The URL is the configuration

        There is no database and no registration. Every request carries the source, the branch or folder and the path. Delete the URL and the site is simply no longer referenced.

        Two sources, one engine

        GitHub and Google Drive share the same validation, MIME, caching and error machinery, so behaviour stays consistent no matter where the files live.

        Stateless by design

        Each invocation resolves one request and returns one response. Only short-lived, in-memory folder listings are cached, and only for a warm instance.

        Security

        How requests are kept safe

        WebProxyLive is a narrow, single-purpose proxy. Each protection below is enforced in code on every request.

        Strict input validation

        Owners, repositories, branches, folder IDs and every path segment are matched against strict patterns before use. Control characters and null bytes are rejected.

        Path traversal is impossible

        .., backslashes and oversized or overly deep paths are refused. Drive segments are resolved one at a time inside the selected folder, so escape cannot occur.

        No arbitrary URL fetching

        The destination is always built from validated identifiers. A visitor can never supply a host, a scheme or a full URL for the server to fetch.

        Host allow-list + redirect checks

        Requests may only reach GitHub and Google owned hosts. Every redirect hop is re-validated against the same allow-list before it is followed.

        HTTPS only

        Upstream traffic is HTTPS. Plain http:// destinations are never constructed or followed.

        Header sanitisation

        Only a small, known set of upstream headers is passed through. Upstream cookies and hop-by-hop headers are dropped, and safe security headers are added.

        File size limits

        Responses above 25 MB are refused with a clear explanation, keeping the proxy fast and preventing accidental bandwidth abuse.

        Correct MIME handling

        Types are derived from the file extension. Extension-less files are served as plain text so source files can never be rendered as markup.

        Deploy to Vercel

        1. Push this project to a Git repository.
        2. Import it at vercel.com/new. The framework preset can stay “Other”.
        3. No environment variables are required. Optionally set GITHUB_TOKEN to raise GitHub's rate limit, or DRIVE_API_KEY to use the Drive API listing.
        4. Deploy. The rewrites in vercel.json wire the public URLs to the Python functions.

        Run it locally

        pip install flask
python app.py                 # http://127.0.0.1:8000
python app.py --port 8080     # different port
python app.py --no-open       # no browser
python app.py --debug         # auto-reload

        The launcher reuses the exact production backends in api/, so local behaviour matches deployment.

        Current limits

        • Maximum file size: 25 MiB.
        • Maximum path segments: 40; maximum segment length: 255.
        • Upstream timeout: 15s.
        • Sources must be public. Private repositories and folders are not supported.
        • No server-side execution of any kind.
